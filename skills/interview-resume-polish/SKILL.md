# 简历经历润色（interview-resume-polish）

## 用途

将用户的原始简历经历改写为**可直接投递**的高质量版本：结构清晰、量化充分、痛点驱动、符合用户审美。

核心认知：**润色的价值不在改字，而在把被埋没的事实挖出来放到正确位置。**

## 何时使用

- 用户提供简历原文（任何格式）要求润色 / 改写 / 量化 / 适配岗位
- 用户提供实习或项目素材（文档、飞书链接、截图、口述）要求写成简历经历
- 用户要求按 STAR 重构、按岗位差异化、做行业竞品对标
- **默认适配岗位**：互联网产品 / 产运 / 销售类中文简历；其他岗位或英文简历先走文风基准判定（见下）

**与 `tailored-resume-generator` 的分工**：基于**候选人已有简历/素材做改写、量化、校验**（本技能主打，中文为主）→ 用本技能；**只给 JD、从零生成定向英文简历**、无本人原始素材 → 用 tailored-resume-generator。两者可串联：先生成初稿，再用本技能校验润色。

## 硬约束（用户审美基准，违反即返工）

1. **文风基准判定前置**：动笔前按 `references/style-guide.md` 第〇节判定——有范例以范例提炼为准；互联网产品/产运/销售岗默认套用五铁律；其他岗位/语言须先与用户确认文风基准
2. **文风五铁律**（详见 `references/style-guide.md`）：标签开头、痛点融入行动、行动分号分层、结果双件套收尾、术语直接上一段式
3. **长度**：单模块 150–210 字，超过 250 字必须压缩
4. **数字加粗**；无数字的概念词不加粗
5. **缺口用〔待补〕占位，严禁编造数字**；改动任何数字前必须核对原文
6. **竞品公司名不进简历正文**，只以方法论术语形式出现（分层匹配、抽检退回、rubric 等）
7. **每个模块 STAR 完整**——尤其不能缺 T（任务目标）
8. **素材归属优先校验**（前置关卡，见下）
9. **范例仅作文风参考，内容以真实素材为准**：style-guide 正例只示范句式与结构，其公司/数字/经历内容严禁写入其他候选人简历；简历事实**全部来自用户上传的简历与素材**，竞品/行业方法论**全部来自当次任务的联网调研**，范例与技能文件中的既有数据都不得当作事实来源

## 执行流程（六步 SOP）

| # | 步骤 | 核心动作 | 交付检查 |
|---|---|---|---|
| 0 | **归属校验**（前置） | 素材多方来源时，先比对身份指纹（姓名 / 毕业时间 / 邮箱 / 文档更新人时间线） | 归属确认后再提取内容 |
| 1 | **输入诊断** | 盘点素材 → 输出原文问题清单 | 差异化经历是否被埋没？素材里有没有金子没用上？ |
| 2 | **岗位解码** | JD 拆解 + 竞品调研（调研行业通行方法论，非竞品产品功能） | 调研产出"能力坐标系"而非功能清单 |
| 3 | **经历盘点** | 事实挖掘 + 数据取证 | 每个数字有出处；缺口列〔待补〕 |
| 4 | **匹配映射** | 能力矩阵 + 差距分析 | 每段经历支撑哪个能力维度 |
| 5 | **重构表达** | 结构重组 + 文风统一 + 量化 | 符合文风五铁律 |
| 6 | **校验迭代** | STAR 检验 + 流畅度 + 穿帮排查 | S/T/A/R 齐否？口述是否顺？ |

详细操作与检查清单见 `references/sop-detail.md`。

## 素材提取工具

- **docx**：`python3 scripts/extract_material.py <file.docx>`——解析 `word/document.xml`，支持 sdt 内容控件与嵌套表格，表格按 ` || ` 保留行列结构，比编辑器预览更完整（MCP 预览会截断长文本，简历常整表存放）；联系方式常藏页眉页脚，疑似缺失时加 `--full`
- **html**：`python3 scripts/extract_material.py <file.html>`——剥离 script/style/base64 后提取正文，表格同样保留 ` || ` 结构
- **pdf**：`python3 scripts/extract_material.py <file.pdf>`——优先 pypdf，未安装自动回退系统 pdftotext；正文提取极少时会提示疑似扫描件，此时改用视觉读取
- **扫描件 / 图片简历**：脚本无能为力的格式，直接用视觉读取（Read 工具读图/读 PDF 页）
- **飞书文档**：使用 `lark-doc` skill 的 `docs +fetch --doc "<url>" --doc-format markdown`；若 lark-cli 未登录或无权限，**不要反复重试**，请用户导出为 docx/pdf 后走本地提取

## 交付物规范

**内容四件套**（同一文件交付，润色稿在前、附录在后）：

1. **润色稿**：按能力视角拆模块（如 平台设计 / 技术纵深 / 用户运营），每模块 = 「标签：」+ 痛点融入式一段
2. **待补数据清单**：表格列出缺口项、影响、取证来源
3. **穿帮风险提示**：时间线 / 名称口径 / 职责边界三类必查
4. **行业锚点 + 60 秒口述版**（可选/建议）：竞品方法论对标只作面试谈资不写进简历；口述版随稿交付

**文件格式与版本**：

- 默认产出 **Markdown 文件**，存当前会话工作目录的 `简历润色/` 子目录
- 命名：`简历润色_<候选人>_<岗位>_v<N>_<YYYYMMDD>.md`（候选人用姓名缩写或代称，避免全名散落文件名）
- 每轮迭代**新存 v2/v3 版本文件，不覆盖旧版**，与 SOP 第 6 步"记录版本号"对应
- 用户要可编辑 Word 投递版 / PDF → 以终稿 md 为源，用 `documents` skill 转换为 docx/pdf，转换后仍需按"交付前三轮自检"核对格式无丢失
- 交付时在回复中给出文件链接，并摘要说明本版相对上一版的改动点

## 交付前三轮自检

1. **结构轮**：模块划分是否按能力视角？叙事主线是否清晰？
2. **文风轮**：是否符合五铁律？是否超长？是否还有独立背景句？
3. **事实轮**：数字是否与原文一致？归属是否正确？待补项是否标注？
