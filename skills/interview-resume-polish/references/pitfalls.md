# 高频错误与防范（血泪教训清单）

> 每次任务开始前先读本文件。以下五类错误均在真实会话中发生过，每一条都导致了返工。

---

## 一、归属混用（最高危）

**症状**：把 A 的简历素材用到了 B 的简历上。

**真实案例（已脱敏，姓名以候选人 A/B 代称）**：处理候选人 A 的简历时，从同目录下候选人 B 的简历文件中提取其三段实习经历，当作"A 的其他实习经历"重写 → 用户指出"B 的经历混入了" → 两轮工作全部作废。

**根因**：多份简历同在本地，提取前未做归属校验。

**防范（前置关卡，不可跳过）**：

| 校验项 | 说明 |
|---|---|
| 姓名 / 邮箱 / 电话 | 最直接的身份指纹 |
| 毕业时间与学校 | 学校不同、毕业年份差异明显时一比对即穿帮 |
| 文档更新人与元数据 | 协作文档内"预计毕业时间"等字段常暴露归属 |
| 实习时间线是否自洽 | 与简历其他部分交叉验证 |

**动作**：素材多方来源时，**先出归属确认表给用户确认，再动手**。

---

## 二、事实误植（数据与成果归属错误）

**症状**：把甲模块的成果写进乙模块，或把不属于本人的成果写进简历。

**真实案例（数据已泛化）**：
- 把自动化 benchmark 的多模型横评规模写成众测平台的成果——实际众测每轮只有少量模型参与；
- 基于非本人署名的项目文档写了评测集题量、Leaderboard 模型数等成果，用户确认"没有做过"。

**防范**：
- 每个数字标注来源文件；
- 同一数字只出现在正确的模块；
- 交付前逐项问："这个成果的载体是哪个产品？参与规模是多少？"

---

## 三、背景赘述（文风问题）

**症状**：独立背景段落 + 冗长铺垫，行动被推到第二段。

**真实反馈**："背景描述可以融到解决的痛点里去，不用过多赘述背景了。"

**防范**：遵循 `style-guide.md` 铁律 2——痛点作前置短语融入行动；背景最多一句收束，用并列短语不展开细节。

---

## 四、超长（单模块超过 250 字）

**症状**：一个模块塞 3 个动作 + 三要素展开，280 字以上。

**真实反馈**："太长了不够简洁。"

**防范**：
- 单模块 150–210 字；
- 压缩四手法：行业全称收进标题、删与背景重复的问题声明、箭头式指标、合并同类动作；
- 动作超过 3 个时，考虑拆成两个模块或按重要性取舍。

---

## 五、亮点埋没（最能体现润色价值的一类）

**症状**：素材里有金子，但简历里看不到。

**真实案例**：
- 用户口述的"众测平台 0-1 + Case 平台 0-1"完全没有进简历（简历只写了零散流程优化）；
- 飞书文档里的"6 个月 6 轮迭代""平台 CLI""Case 自动复现"未被使用；
- docx 版里的"**1 个月内完成上线**""**负责 PRD 与交互原型**"未并入（比"交互设计"更有力）。

**防范**：
- 输入诊断阶段必做三问：① 哪些差异化经历没进简历？② 提供的素材里有哪些数据/成果没用上？③ 有没有多个版本，哪版的表述更强？
- 优先挖"从 0 到 1""平台化""体系搭建"类结构性成果——它们是区分执行者与 Owner 的关键。

---

## 六、其他必查项

| 类别 | 检查点 |
|---|---|
| 时间线 | 入职 / 毕业 / 项目周期是否自洽；平台初版时间是否早于本人入职（会挑战"从 0 到 1"） |
| 名称口径 | 同一产品是否出现多个叫法（如"众测平台"vs"AI Agent 评测平台"），需统一 |
| 职责边界 | 多人协作项目要说清自己负责的部分；文档更新人含多人时需准备分工说明 |
| 编造风险 | 缺口一律〔待补〕；推断性包装需标注并提示用户核对（如"平衡成本与质量"是推断） |
| 竞品名 | 竞品公司名不进简历正文，只留方法论术语 |
| 数字改动 | 任何数字改动前必须回原文核对——严禁"顺手优化"数字 |
